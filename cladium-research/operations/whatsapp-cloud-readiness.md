# WhatsApp Cloud API readiness report

Status: **not enabled. Report and disabled adapter scaffold only.** Runbook Step 38, `release-gates-v2.md` Gate 8's own bullet: "WhatsApp Cloud remains off until WABA ownership, templates, signature verification, opt-in/opt-out, retention, and staff response operations pass review."

**This step does not send, receive, or process any real WhatsApp Cloud API message.** `FEATURE_WHATSAPP_CLOUD` stays `false` in `.env.example`; no code path here can flip it. What exists after this step: this readiness checklist, a real (but never-called) outbound adapter shaped to Meta's documented Cloud API contract (`modules/integrations/whatsapp-client.ts`), and one webhook route (`/api/whatsapp/webhook`) that fails closed — rejects every request — while the flag is off, exactly the way `/api/vapi/tools`/`/api/vapi/webhook` (Step 32) and `POST /api/meta/track` (Step 37) already fail closed without their own credentials. Click-to-WhatsApp (Step 35) is unaffected and unrelated — that is a plain `wa.me` link, not the Cloud API this report is about.

## Why this is a separate, later gate from click-to-WhatsApp

Click-to-WhatsApp (Step 35) opens the business's real WhatsApp app/web client with a prefilled message — no Meta app review, no template approval, no webhook, no automation; a human at the business reads and replies to every message personally. WhatsApp Cloud API is a different thing entirely: an automated, programmatic channel (sending template messages, receiving delivery/read receipts and inbound replies via webhook) that requires Meta's own approval process and materially changes who/what is allowed to message a guest and how. `CLAUDE.md` and Gate 8 keep these deliberately separate; enabling one never implies the other.

## Prerequisites (all must be true before `FEATURE_WHATSAPP_CLOUD` is ever set `true` in any environment)

- [ ] **Business-owned WABA (WhatsApp Business Account)**: the business, not a developer/agency account, owns the WABA and the underlying Meta Business Manager. Ownership must be transferable/auditable — never a personal or contractor-held account the business could lose access to.
- [ ] **Phone number registration**: the official business number (`business/facts.ts`'s `WHATSAPP_DISPLAY`, already owner-confirmed for click-to-WhatsApp) is registered to the Cloud API, or a decision is made to use a separate dedicated number — registering the same number retires it from the personal WhatsApp Business app the owner may currently use to reply manually.
- [ ] **Meta app review and message template approval**: every outbound template message (a booking-request acknowledgment, a staff reply, etc.) is submitted to Meta for approval before use; utility/marketing template categories are chosen correctly (marketing templates additionally require `META_MARKETING`-equivalent consent, per Gate 8's separate Meta consent requirement — Step 36/Step 37's `META_MARKETING` consent category and Cloud API opt-in are related but not identical, and must not be conflated).
- [ ] **Signature verification**: every inbound webhook delivery is verified via Meta's documented `X-Hub-Signature-256` header (HMAC-SHA256 over the raw request body, keyed by the Meta app secret) before any payload content is trusted — built now (`modules/integrations/whatsapp-webhook-auth.ts`), never bypassable while the feature is enabled.
- [ ] **Webhook subscription verification (handshake)**: Meta's `GET` challenge-response handshake (`hub.mode`/`hub.verify_token`/`hub.challenge`) is answered correctly using a secret verify token distinct from the signature secret — built now, gated the same way.
- [ ] **Webhook dedupe**: `webhook_events` (`data-model-v2.md` §6, already migrated — Step 9) already has a `(provider, provider_event_id)` unique constraint and a `WHATSAPP` provider enum value ready to use; a live integration must record each processed WhatsApp message/status id there before acting on it, the same idempotency discipline `execute-vapi-tool-calls.ts`'s `toolCallId` handling already established (Step 32). Not wired to real message parsing in this step — no live traffic exists to validate the real payload shape against, the same reasoning `vapi-client.ts`'s JWT claims were flagged unverified until Step 33 installed the real SDK and could check.
- [ ] **Opt-in / opt-out**: a guest must have opted in (their own message, or an explicit consent action — never inferred from a takeaway/booking/event request alone) before receiving any Cloud API message, and a clear, honored opt-out path (e.g. replying "STOP", or an explicit unsubscribe) must exist before this goes live. This is a distinct consent surface from `modules/consent/`'s four existing categories (`ESSENTIAL_PREFERENCES`/`META_MARKETING`/`MICROPHONE`/`RECORDING`, Step 36) — none of which cover WhatsApp messaging opt-in — so a fifth category (or a dedicated mechanism) needs designing before this goes live, not assumed to already exist.
- [ ] **Retention**: inbound/outbound message content, delivery/read receipts, and any stored conversation history have an owner-approved retention and deletion schedule — same standing gap Gate 0 already tracks for the general privacy notice (D-021/Step 36's `/privacy` page), not a new one invented here.
- [ ] **Cost**: Meta's per-conversation pricing (varies by category and country) is understood and budgeted; a runaway automated flow must have a rate/cost ceiling before going live — no such ceiling is built in this step, since nothing sends yet.
- [ ] **Escalation ownership**: a documented staff response process — who monitors inbound Cloud API messages, expected response time, and the handoff back to a human when automation cannot help — mirrors the existing safe WhatsApp-pointing fallback the concierge already uses (`orchestrator.ts`'s `escalationReply`, Step 27/35) but for the *reverse* direction (Meta → staff), which does not exist yet.
- [ ] **Staff ownership**: a named role (owner/manager, per `staff_role` — Step 10) accountable for template content changes, WABA health, and Meta policy compliance, distinct from day-to-day message handling.

## What is built now (this step)

- `modules/integrations/whatsapp-client.ts`: a thin, real-shaped `WhatsAppCloudClient` interface plus one real adapter (`createWhatsAppCloudClient`) matching Meta's documented Cloud API send-message contract (`POST /{phone_number_id}/messages`) — never throws at construction (same "fail only when actually used" shape as every other adapter here: `vapi-client.ts`, `meta-client.ts`), fails closed (throws) inside `sendTemplateMessage` when `WHATSAPP_PHONE_NUMBER_ID`/`WHATSAPP_BUSINESS_ACCOUNT_ID`/`WHATSAPP_ACCESS_TOKEN` aren't all configured. **Never called by any route or trigger in this codebase** — a pure, tested, unused-by-design scaffold, ready for the day a real integration is approved and wired.
- `modules/integrations/whatsapp-webhook-auth.ts`: `verifyWhatsAppWebhookSignature` (Meta's real `sha256=<hex>` `X-Hub-Signature-256` scheme — confirmed against Meta's current public webhook documentation, not a guess) and `verifyWhatsAppWebhookChallenge` (the `hub.mode`/`hub.verify_token`/`hub.challenge` handshake).
- `GET/POST /api/whatsapp/webhook`: both check `FEATURE_WHATSAPP_CLOUD` **first**, before anything else — off means a `404` (`featureDisabled()`, same "a disabled feature must not confirm it exists" convention `/api/vapi/token` established in Step 31), matching this step's own evidence bullet: "flag-off routes fail closed." When (hypothetically) enabled, `GET` answers the subscription handshake and `POST` verifies the signature before returning `200` — it does not yet parse or store the payload (no live traffic exists to validate the real inbound message schema against, and no dedupe/storage wiring exists yet — tracked below).
- `parseWhatsAppCredentials`/`parseWhatsAppWebhookSecret`/`parseWhatsAppWebhookVerifyToken` (`lib/env.server.ts`) — narrow, fail-closed-to-`undefined` accessors, the same shape as every other optional third-party credential here (`parseMetaCredentials`, `parseVapiWebhookSecret`).

## What is explicitly not built (tracked in `.continuum/TASKS.md`, not forgotten)

- Real inbound message parsing/storage into `webhook_events`, and the dedupe check against `(provider, provider_event_id)` — needs the real payload shape confirmed against live traffic or Meta's current schema docs, the same "verify before shipping a guess" discipline Step 33 applied to Vapi.
- A fifth consent category (or equivalent mechanism) for Cloud API opt-in/opt-out, distinct from `modules/consent/`'s existing four.
- Any actual outbound send wired to a real trigger (e.g. sending a booking acknowledgment) — `sendTemplateMessage` exists and is tested in isolation but is not called from anywhere.
- Template content and Meta's approval of it.
- The reverse-direction (Meta → staff) escalation/notification flow — `modules/staff/notification-handlers.ts` (Step 25) could plausibly gain a `whatsapp_inbound` handler later, following the exact same outbox-dispatcher pattern already proven for staff notifications, but nothing here assumes that shape yet.

## Turning this into a live integration

Only after every prerequisite above is checked and the owner has explicitly approved going live:

1. Configure `WHATSAPP_PHONE_NUMBER_ID`/`WHATSAPP_BUSINESS_ACCOUNT_ID`/`WHATSAPP_ACCESS_TOKEN`/`WHATSAPP_WEBHOOK_VERIFY_TOKEN`/`WHATSAPP_APP_SECRET` in the target environment's secret store (never committed — same pattern as every `VAPI_*`/`META_*` credential, `deployment-target.md`'s table).
2. Set `FEATURE_WHATSAPP_CLOUD=true` in that environment only (development/preview first, matching `docs/vapi-deployment.md`'s promotion order).
3. Build the real inbound message parsing/dedupe/storage wiring named above, verified against real Meta traffic before trusting it.
4. Design and build the fifth consent category (or equivalent) for Cloud API opt-in/opt-out before any automated send reaches a real guest.
5. Wire actual outbound sends to real triggers only after their templates are Meta-approved and the owner has signed off on the exact wording.
