## D-040 — Step 36 consent and privacy controls: a genuine append-only ledger with a fail-closed default per category, real server-side enforcement (not just a UI toggle), a narrow auditable exception added to the schema for retention, and an honest not-yet-published privacy page

- Decision: `modules/consent/` implements the four distinct categories `data-model-v2.md`'s `consent_events` names (`ESSENTIAL_PREFERENCES`/`META_MARKETING`/`MICROPHONE`/`RECORDING`) as a real append-only event ledger (`lib/domain/consent-event.ts`, `consent-store.ts`) — the exact same shape as `status_events`/`audit_events` (Step 19), never a bespoke mechanism. `consent-service.ts#getConsentSnapshot` folds the ledger into "what's true now" per category, defaulting `ESSENTIAL_PREFERENCES` to granted (it already governs the locale/theme cookies Steps 13–14 built with no consent gate at all, and disabling it would break the language/theme switcher every guest relies on) and every other category to NOT granted absent an explicit event — the fail-closed default `release-gates-v2.md` Gate 8's "avoids exposing customer data... unless the guest explicitly chooses it" and `production-architecture-v2.md` §12's consent requirements both imply. `CONSENT_POLICY_VERSION` (`policy.ts`) is the "versioned-policy" the runbook's evidence bullet names — a category's last-recorded version mismatching the current one marks it `stale`, so a real policy change re-prompts a guest rather than silently keeping a stale grant.

Step 37's Meta adapter will call the exact same `hasConsent(deps, sessionId, 'META_MARKETING')` for "analytics blocking" — this step deliberately built and tested that primitive now, without waiting for the adapter that will consume it, so Step 37 has nothing left to design on the consent side.
- A real, previously-undiscovered schema gap: Step 9's `consent_events_append_only` trigger blocks UPDATE/DELETE *unconditionally*, for every role including service_role — correct for `status_events`/`audit_events`, but it structurally cannot support the "deletion/retention job" this step's own evidence bullet requires, since there would be no way to ever remove an expired row even from a privileged context. No ordinary application code path, and no raw `DELETE` statement from any caller, can ever remove a row. `CONSENT_EVENT_RETENTION_DAYS` (400 days) is an explicitly-flagged conservative placeholder pending the owner-approved retention schedule `release-gates-v2.md` Gate 0 still lists as unchecked — safe to shorten, not to lengthen, without that review.
- "Hide unapproved legal pages" (the runbook step's own wording) and Gate 0's unchecked "privacy notice... owner/legal reviewed" bullet mean no real privacy-notice prose can be published yet — `CLAUDE.md`'s "never publish placeholder legal pages" is non-negotiable regardless of how much of this step is otherwise buildable. `/privacy` (new) resolves this the same way `menu/page.tsx` resolved the unpublished-menu problem in Step 17 (D-021): an honest "not published yet, here's how to reach us" notice, never invented legal text, paired with the real, fully-working consent grant/revoke controls — those are not gated on owner content at all, since the mechanism itself needs no legal sign-off to be genuinely useful today.

## D-036 — Step 32 authenticated Vapi tools and webhooks: HMAC/timestamp/replay verification fully reused from Step 12, `toolCallId` idempotency fully reused from Step 19, tool execution dispatches through the exact same registry text chat uses

- Decision: `modules/voice/webhook-auth.ts#verifyVapiWebhookRequest` is a thin Vapi-specific wrapper around `lib/security/webhook.ts`'s already-generalized, already-tested `verifyWebhook` (Step 12) — no new HMAC/timestamp/replay logic anywhere. The only new pieces are the header names (`x-vapi-timestamp`/`x-vapi-signature`, explicitly flagged as this codebase's own choice, unverified against a real Vapi Custom Credential configuration) and a fail-closed wrapper: an unconfigured `VAPI_WEBHOOK_HMAC_SECRET` (`parseVapiWebhookSecret`, new — returns `undefined` rather than throwing, same shape as `parseCronSecret`) rejects every request as `BAD_SIGNATURE` before ever calling the real verifier, mirroring `cron-auth.ts#verifyCronAuthHeader`'s "an unconfigured secret must never mean accept anything" reasoning exactly. Replay dedupe's `eventId` is a SHA-256 hash of the raw signed request body, not a field parsed out of Vapi's payload — correct regardless of exactly which envelope fields a given Vapi delivery carries, and it correctly identifies "the same signed delivery, resent byte-for-byte" as a replay by construction.
- `modules/voice/tools/execute-vapi-tool-calls.ts#executeVapiToolCalls` dispatches every tool call through `modules/concierge/tool-registry.ts#dispatchToolCall` — the exact same registry and domain services Step 27's text orchestrator calls, never a second implementation — and serializes each result identically to `orchestrator.ts`'s own `tool_result` convention (`JSON.stringify(ok ? value : {error: message})`). This is the literal mechanism behind `deployment-target.md`'s "the voice agent passes the same...tests as text chat": there is structurally only one tool implementation for both surfaces to diverge from.
- `toolCallId` idempotency reuses Step 19's `runIdempotent`/`IdempotencyStore<R>` completely unchanged — a new scope (`vapi-tool-call`) and a new key source (Vapi's own `toolCallId`, the "at-least-once delivery" identifier `production-architecture-v2.md` §9 names for exactly this purpose) is the only new wiring; the same-key/different-fingerprint-is-rejected and same-key/same-fingerprint-replays contract needed no re-derivation.
- Bounded execution has two independent limits: `MAX_TOOL_CALLS_PER_WEBHOOK` (5) caps how many calls from one delivery are ever dispatched — anything beyond that gets an honest per-`toolCallId` rejection result, never silently dropped or executed anyway, so Vapi/the model always gets *an* answer for every call it made; `TOOL_CALL_TIMEOUT_MS` (8s) races each individual dispatch so one hung domain call can never block the whole webhook response. `dispatchToolCall` is dependency-injectable in `ExecuteVapiToolCallsDeps` specifically so this codebase's own tests can prove the timeout path deterministically (a fake dispatcher that never resolves, combined with vitest fake timers) rather than depending on a real tool being artificially slow.
- `modules/integrations/vapi-webhook.ts`'s tool-calls envelope schema (`message.type`/`toolCallList`/`call`) is explicitly flagged, the same way `vapi-client.ts`'s JWT claims are (D-035), as a best-effort mapping to Vapi's documented format, never verified against live traffic — deliberately *not* a `strictObject`, since an unknown field from a third-party payload is not a bug the way it would be in this codebase's own API contracts. `localeForAssistantId` derives the caller's locale authoritatively from which of *our own* two configured assistant ids (`VAPI_ASSISTANT_EN_ID`/`VAPI_ASSISTANT_UR_ID`) the call belongs to — a more robust choice than trusting a client-supplied `metadata.locale` field, since we already control that mapping server-side. `sessionIdForCall` uses a real `call.metadata.sessionId` when the (future, Step 33) voice UI sets one, or a call-scoped synthetic id (`voice:${callId}`) otherwise — the fallback can never collide across two different real Vapi calls, and a missing real session id degrades to "no cart found" for `viewCart`/`getRequestStatus`, never a cross-guest data leak.
- `/api/vapi/webhook` (generic call-lifecycle events — call started/ended, transcript, end-of-call report) is authenticated identically but deliberately does nothing with an event beyond acknowledging it and logging only its `type` (redacted-safe, never the event body, which could carry guest speech content) — the same "build the verified/authenticated layer now, wire real handling once there's a reason to" pattern Step 26 (tools with no caller yet) and Step 27 (orchestration with no UI yet) already established. Nothing downstream consumes a lifecycle event today; `conversation_summaries` was explicitly not created (Step 9).
- Evidence: 39 new focused tests across three files — webhook-auth (valid/invalid-signature/tampered-payload/stale-timestamp/replayed/differently-signed-not-blocked/unconfigured-secret-fails-closed/missing-header); envelope-schema and helper-function tests (tolerant of unknown fields and string-encoded arguments, strict about the required shape, locale/session derivation edge cases); execution tests (a real end-to-end dispatch through `getVenueInfo` proving the same-domain-service claim non-circularly, an unknown-tool-name NOT_FOUND parity check, bounded-list overflow handling with correct per-call ids, toolCallId dedupe and fingerprint-mismatch-is-a-conflict, and a genuine `vi.useFakeTimers`-driven proof that a dispatch which never resolves still returns a bounded result at exactly `TOOL_CALL_TIMEOUT_MS`). 890 tests total (73 files); full `npm run verify` passes, including a production build listing `/api/vapi/tools` and `/api/vapi/webhook`. Live check confirmed both routes reject an unauthenticated request (401) and a malformed body (400) correctly; no live `VAPI_WEBHOOK_HMAC_SECRET` traffic is possible in this sandbox.

## D-035 — Step 31 short-lived Vapi browser token service: a hand-rolled spec-shaped HS256 JWT (never a new dependency), a claim shape flagged as unverified against a live credential, and the first route in this codebase to actually enforce a `FEATURE_*` flag

- Decision: `lib/security/jwt.ts` implements a real RFC 7519 compact HS256 JWT (`base64url(header).base64url(payload).base64url(HMAC-SHA256 signature)`) using only `node:crypto` — no new dependency. This differs deliberately from `security/session.ts`'s simpler two-part signed-cookie format: a session cookie is only ever read back by this same server, but a Vapi token is verified by a *third party* (Vapi's own SDK/API) using a standard JWT library, so the wire format must be genuinely interoperable, not merely internally consistent. `signJwt`/`verifyJwt` inject `iat`/`exp` themselves, silently overriding any caller-supplied `iat`/`exp` claim keys rather than letting them be shadowed — tested directly.
- `modules/integrations/vapi-client.ts#createVapiTokenIssuer` mirrors `anthropic-client.ts#createAnthropicChatClient` (D-031) exactly: never throws at construction, reads Vapi credentials lazily only inside `issueToken`, so importing it at process start (`modules/voice/deps.ts` does) can never crash an unrelated route. Its restricted-JWT claim shape (`orgId` + `token.restrictions.allowedAssistantIds`/`allowedOrigins`/`allowTransientAssistant`) is a **best-effort mapping to Vapi's documented format, explicitly flagged in the module's own doc comment as never verified against a live `VAPI_PRIVATE_KEY`** — the same standing sandbox limitation as `ANTHROPIC_API_KEY` (D-031) and the assistant-creation procedure (D-034). If the real shape differs, only this one function needs to change — callers depend on the `VapiTokenIssuer` interface, never the claim shape directly (ADR-0008 reversibility). Tracked in `.continuum/TASKS.md` as a pre-launch verification item.
- `modules/voice/token/issue-vapi-token.ts#issueVapiToken` is the orchestration layer, mirroring `orchestrateTurn`'s (Step 27) shape: a feature-flag check first (`FEATURE_VOICE_EN`/`FEATURE_VOICE_UR`, selected by the requested locale) — **the first route in this codebase to actually read a `FEATURE_*` flag**, closing part of the gap Step 24 found (`FEATURE_TAKEAWAY_REQUESTS`/`FEATURE_BOOKING_REQUESTS`/`FEATURE_EVENT_REQUESTS` remain unenforced, still tracked) — then a dedicated rate limit (`VAPI_TOKEN_RATE_LIMIT_RULE`: 5/min per session, tighter than the text concierge's 10/min, since minting a voice-call credential is a heavier grant than one chat turn), then the actual issuance. A thrown credential error (malformed/missing Vapi config) never reaches the client with its own message — only a safe `INTERNAL` response and an `errorType` in the server log, the same "never leak detail" shape `orchestrateTurn`'s catch block uses.
- `POST /api/vapi/token` reuses Step 20's `parseMutatingRequest` guard completely unchanged (session resolution, CSRF token, origin allowlist) — no new auth mechanism for a second entity, same "wire an existing mechanism to a new route" pattern as Steps 22/23. CSRF is kept even though nothing is written to a domain record: a forged cross-site POST minting a token against a victim's session/rate-limit budget is exactly the class of request CSRF protection exists to block. The origin embedded in the issued token's restrictions is always the server's own configured `NEXT_PUBLIC_APP_URL` (`parseAppUrl()`), never the request's raw `Origin` header — defense in depth even though that header was already checked against the same value by the guard.
- Evidence: 24 new focused tests across three files — `jwt.test.ts` (round-trip, tamper/wrong-secret/malformed/expired/exact-boundary rejection, caller-supplied `iat`/`exp` never leaking through); `vapi-client.test.ts` (correct, distinct assistant id per locale; full restriction-claim shape; TTL correctness; construction never throws even unconfigured; `issueToken` throws when credentials are missing; the issued response never contains the private key); `voice-token-issuance.test.ts` (flag-gating including that one locale's flag does not unlock the other; per-session rate-limit enforcement and isolation; safe fallback with no leaked credential detail on a thrown error). 851 tests total (70 files); full `npm run verify` passes, including a production build listing `/api/vapi/token` and a client-bundle scan confirming no Vapi credential material reaches the browser. No live Vapi credential exists in this sandbox — only the fail-closed/validation paths are exercised, the same standing limitation as every provider integration since Step 27.

## D-029 — Step 25 outbox dispatcher: one shared, atomically-claimed outbox store across all three entities; Supabase Realtime is deferred (D-017), polling the durably-dispatched result is the actual delivery guarantee for now (ADR-0007)

- Decision: `OutboxEvent` (`lib/domain/outbox.ts`) gained `id`/`version` — nothing before this step ever needed to address one specific outbox row, only append and bulk-read. `lib/domain/outbox-store.ts`'s `OutboxStore` adds `claimBatch` (one atomic conditional operation claiming due-`PENDING`-or-stale-`CLAIMED` rows, oldest first — the exact Step 21 lesson applied here: never a separate read-then-write) plus `markDelivered`/`markRetry`/`markTerminal`, each version-checked. `lib/domain/outbox-dispatcher.ts`'s `runDispatchCycle` claims a bounded batch and resolves every claim to `DELIVERED`, retried with bounded exponential backoff, or `FAILED` (terminal) once `maxAttempts` is reached — a row is never left `CLAIMED` with nothing decided, and a row with no registered handler for its `destination` fails terminal immediately rather than being retried forever for a handler that will never exist.
- One outbox, not three: `data-model-v2.md` §6 has a single `outbox_events` table, not one per entity, so `modules/{takeaway,bookings,events}/deps.ts` now all point their `outbox` field at one shared singleton (`modules/notifications/deps.ts`) instead of each building its own private `createInMemorySink()`. This lets one dispatcher drain every entity's notifications in one pass, matching the real schema, and required no type changes to `submission-service.ts`/`staff-transition.ts` (both still declare `outbox: AppendOnlySink<OutboxEvent>`; `OutboxStore` structurally satisfies that shape).
- What handles a claimed event: `modules/staff/notification-handlers.ts`'s `staff_notification` handler (the only destination in use today — ADR-0007: "the outbox schema is destination/payload-agnostic," so a future channel is an additive registry entry, not a rewrite) upserts into `modules/staff/notification-store.ts` by the outbox event's own id, which is what makes it idempotent — the dispatcher may invoke a handler twice for the same event if the process crashes between the handler succeeding and the row being marked `DELIVERED` (the same at-least-once ambiguity any such system has), and an upsert-by-id absorbs that without a duplicate.
- Realtime is explicitly deferred, not built: no live Supabase project exists (D-017), so `app/staff/dashboard.tsx` polls `GET /api/staff/notifications` instead of subscribing to a channel. This is not a lesser substitute for what the runbook step asks — ADR-0007 itself frames Realtime as "a speed-up, not the delivery guarantee," and the outbox's actual guarantee (a row reaches `DELIVERED` and becomes durably queryable) is exactly what polling already observes; Realtime would only make staff notice faster, a UX improvement to add once a live project exists, not a correctness gap today.
- The cron trigger: `app/api/cron/outbox-dispatch` (`GET`, authenticated via `Authorization: Bearer $CRON_SECRET` — `deployment-target.md` names this exact pattern for "authenticated outbox/retention jobs") runs one bounded cycle and returns redacted counts only (claimed/delivered/retried/terminal — never payloads or guest data). Added `lib/env.server.ts`'s `parseCronSecret` (returns `undefined` rather than throwing, unlike `parseSessionSecret`/`parseAppUrl` — a missing `CRON_SECRET` should mean "reject every request," not a 500) and `lib/security/cron-auth.ts`'s `verifyCronAuthHeader` (constant-time comparison, same reasoning as every other secret comparison in this codebase; `false` whenever the secret itself is unconfigured, never "accept anything"). Safe to invoke concurrently or in rapid succession — `claimBatch`'s atomicity is what makes overlapping invocations safe, not anything in the route itself. The actual Vercel Cron schedule is a deployment-step concern (Step 46), not built here.
- Evidence: 34 new focused tests covering exactly the runbook's own evidence bullet — worker overlap (two genuinely concurrent `claimBatch`/`runDispatchCycle` calls never both claim or invoke a handler for the same row), crash/retry (a stale, unresolved claim is reclaimed after `staleClaimMs`; a transient failure retries with a growing backoff and succeeds once due), poison message (a handler that always throws is marked terminal at exactly `maxAttempts` and never claimed or invoked again after that), and terminal-failure visibility (`lastError`/`failedAt` recorded and queryable via `list()`) — plus the notification handler's idempotent upsert and the cron auth header's fail-closed matrix. 684 tests total; full `npm run verify` passes, including a production build listing `/api/cron/outbox-dispatch` and `/api/staff/notifications`. Live check confirmed the cron endpoint fails closed (401, safe generic message) with no `Authorization` header/`CRON_SECRET` configured, and `/staff`'s sign-in page still renders correctly with no regression.

## D-025 — Fixed a real concurrency race in Step 19's idempotency/confirmation-token stores; atomicity/rollback beyond that is deferred to a real DB

- Decision: `lib/domain/idempotency.ts`'s `IdempotencyStore` and `lib/domain/confirmation-token.ts`'s `ConfirmationTokenStore` each replaced a two-step "read, decide, write" (`find`+`begin`, `find`+`markUsed`) with one atomic store operation (`findOrBegin`, `claimIfUnused`) that a real adapter must implement as a single conditional write (e.g. `UPDATE ... WHERE used_at IS NULL RETURNING *`), not a separate read-then-write.
- Why: Runbook Step 21's evidence bullet ("concurrency, double-click, retry, rollback, and atomicity integration tests") is explicitly *not* satisfied by Step 19's sequential tests — checking directly, an explicit `Promise.all` (two calls fired together, not one awaited after the other) proved both the idempotency store and the confirmation-token store let two truly concurrent callers both pass the "not yet started"/"not yet used" check before either wrote back, because `await`ing an async store call always yields to the microtask queue even when the call's own body is synchronous. Sequential tests never exercise this: each call fully completes (including its writes) before the next one starts, so the interleaving the fix targets never happens. `versioned-store.ts`'s `updateIfVersionMatches` was already correct by the same reasoning in reverse — its whole body has no internal `await`, so two calls can never interleave even when invoked concurrently.
- What "atomicity/rollback" still means here: for the in-memory stores, a genuine multi-step failure part-way through (e.g. the second of several snapshot-line writes throwing) has no real rollback, because in-memory `Map`/array writes cannot fail and there is no live database transaction (D-023/D-017) to roll back. `submission-service.ts` already does all validation and computation before any write, so no write happens for a request that was going to fail anyway — that is the property provable now; true multi-write atomicity is a property the real Postgres adapter's transaction must provide later, not something achievable in-memory.
- Evidence: 5 new focused tests using `Promise.all` (not sequential awaits) — a genuine double-click on the same idempotency key/confirmation token resolves to exactly one success and one `IDEMPOTENCY_CONFLICT`/`NOT_FOUND`, never two successes and never zero; a `FAILED` record with a *different* fingerprint still blocks as a mismatch rather than being silently retried. 563 tests total; full `npm run verify` passes.

## D-019 — Theme preference is a separate, unsigned, isomorphic cookie; `/[locale]` is now dynamic

- Decision: the Day/Night preference (`lib/theme/`) is its own cookie (`cladium_theme`), deliberately unsigned and readable/writable by client JS — unlike the locale preference cookie (`lib/i18n/preference-cookie.ts`), which is signed and `HttpOnly`. `app/[locale]/layout.tsx` now calls `cookies()` to render the correct `data-theme` on first paint, which makes `/en` and `/ur` dynamically rendered (`ƒ`) instead of statically prerendered (`●`).
- Why: theme-mode.md states the theme is "separate from language" with no security/routing consequence, unlike locale (open-redirect risk). Signing would buy nothing and would block the instant, no-reload client-side toggle the spec requires (an `HttpOnly` cookie can't be read/written from `document.cookie`). Reading the cookie server-side for a flash-free initial render is unavoidably a per-request operation, so static prerendering of the locale routes is no longer possible — an accepted, necessary trade-off, not a regression to fix later.
- Evidence: `tests/unit/theme.test.ts`, `tests/unit/theme-preference-cookie.test.ts`, `tests/unit/theme-tokens.test.ts`; live browser check of `/en` and `/ur` in both themes, including instant client-side switching (verified with the CSS transition temporarily disabled, since the test harness's hidden preview pane doesn't produce compositor frames to drive a live transition — a tooling artifact, confirmed not to affect a normally-visible browser).

## D-018 — Route group per root layout, not a shared one above `[locale]`

- Decision: the un-localized `/` fallback (`app/(root-fallback)/{layout,page}.tsx`) lives in its own route group with its own `<html>`/`<body>`, instead of a single `app/layout.tsx` shared with `app/[locale]/layout.tsx`.
- Why: Next.js only merges a nested duplicate `<html>` tag's *missing* attributes onto the outer one — it never overwrites an attribute the outer tag already set. The prior shared `app/layout.tsx` set `<html lang="en">` unconditionally and sat above `app/[locale]/layout.tsx` in the tree, so every `/ur` route rendered `lang="en" dir="rtl"` in the browser: `dir` (unset outer) merged through, `lang` (set outer) silently won. Found by loading `/ur` in a real browser and reading `document.documentElement`, not by the unit/build gates, which don't render a DOM.
- Evidence: `npm run verify` passes with the route group in place; manual browser check of `/en` and `/ur` shows correct `lang`/`dir` on both.
