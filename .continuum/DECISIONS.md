## D-059 — Built the missing Supabase password-recovery landing page, a real, previously-unknown gap found live while helping the owner reset a staff account's password

- Decision: `src/app/staff/reset-password/page.tsx` (new) — a client-only page that consumes a Supabase password-recovery session and lets the guest actually set a new password. Found live, not theorized: after the owner's Site URL misconfiguration (`localhost:3000`, default) was fixed so recovery links correctly redirected to the deployed app, resetting still silently did nothing — because no code anywhere in this app ever called `supabase.auth.updateUser({ password })`. Supabase's recovery link only *establishes a session*; the session tokens travel in the URL's hash fragment (browser-only, server never sees it), and landing on any ordinary page with no code to read that hash does nothing while looking like it worked.
- Diagnosed via direct evidence, not guesswork: Supabase MCP `edge_logs` (the real gateway/Kong request log — unlike `auth_logs`, which does not reliably log every password-grant attempt) showed the actual sequence of `POST /auth/v1/recover`, `GET /auth/v1/verify?...type=recovery...`, and confirmed the post-fix `redirect_to` was correct. A separate `DELETE /auth/v1/admin/users/...` attempt found in the same log window was confirmed via `execute_sql` to have had no effect — the account and its `staff_profiles`/`staff_role_memberships` rows were fully intact, consistent with the `on delete restrict` FK blocking it.
- Uses its own browser-only Supabase client (default `detectSessionInUrl`/`persistSession`), deliberately separate from `modules/integrations/supabase-auth-client.ts`'s server-only, stateless-per-call client built for D-050 — that client must never hold a session across a page's lifetime, and this page's whole job is the opposite. Listens for both an already-resolved `getSession()` and the `'PASSWORD_RECOVERY'` `onAuthStateChange` event (real, type-verified against `@supabase/auth-js`'s shipped `.d.ts`, not guessed) to cover either init timing; a 3-second timeout without either firing renders an honest "link is invalid or expired" state rather than hanging. On success, calls `updateUser({ password })` then `signOut()` — this page never touches this app's own staff session cookie or `modules/staff/*`; a successful reset only means the *next* real sign-in via `/staff`'s own form will work.
- Client-side validation only duplicates what's cheap to check locally (length ≥ 8, confirm-match) — the actual password policy enforcement is Supabase's own, unchanged.
- Still required, not something this build process can do: the owner must update the Supabase project's **Site URL** (Authentication → URL Configuration) to `https://cladium-cafe.vercel.app/staff/reset-password` specifically (not just the bare domain) — the dashboard's own "send recovery email" action has no way to override `redirectTo`, so Site URL is what actually determines where the hash-fragment session lands.
- Evidence: `npm run typecheck`/`npm run lint` clean; full `npm run verify` passes, including a production build listing the new `/staff/reset-password` route (prerendered static, correctly — no server-side data dependency) and a client-bundle scan finding no secret/server-only value in the new page's compiled output.

### D-059 follow-up — the real bug behind "no reset form ever appears": `NEXT_PUBLIC_*` was never actually inlined into any client bundle, a structural gap in `lib/env.ts` itself, not a Vercel configuration problem

- The owner then supplied a genuinely valid, unexpired recovery-session hash (`#access_token=...&type=recovery`, not an error) and still saw no form — reproduced directly against the live production site using that exact link (observe-only; the resulting session was never used to change anything). Console showed the identical `ZodError: expected string, received undefined` this project's local sandbox always shows for missing Supabase env vars — except this was the **live deployed site**, which does have these values configured (proven independently: server-side sign-in already works there).
- Root cause, confirmed by evidence, not assumed: fetched the actual deployed client JS chunk (`fetch()` against its `_next/static` URL from the live page) and found **zero** occurrences of the real Supabase project URL or either variable name anywhere in it. `lib/env.ts`'s three accessors (`parseClientEnv`/`parseAppUrl`/`parseSupabasePublicCredentials`) all defaulted their `source` parameter to `process.env` — the *whole object*, passed by reference — with Zod then reading named keys off it dynamically. Next.js's build-time `NEXT_PUBLIC_*` inlining only replaces a **literal, statically-written** `process.env.NEXT_PUBLIC_X` member expression wherever it appears in source text; passing the object reference through a function boundary and reading keys dynamically is invisible to that pass. Server-side this was always harmless — real `process.env` at runtime there — which is exactly why it went undetected through Steps 6/12/20/31/50: every prior caller of these accessors was server-only. `staff/reset-password/page.tsx` (D-059) is the first client-side caller these functions have ever had, so this is the first moment the gap could have been hit.
- Fixed at the root, not just the one call site: each accessor's default is now a literal object built from direct `process.env.NEXT_PUBLIC_X` expressions inside a small `defaultClientEnvSource()` helper in the same file — still evaluated fresh per call (a JS default parameter, not a module-load constant), so server-side behavior (reading the real runtime environment) is completely unchanged, but now the compiler has actual literal text to find and replace for any future client caller too, not only this one.
- Evidence: full `npm run verify` passes clean (1099 unit tests unaffected — no test relied on the old pass-by-reference shape); live re-verification after deploy: fetched the newly built client chunk and confirmed the real Supabase project URL string is now present in it, where it was completely absent before.

### D-059 follow-up — the actual, final root cause of every remaining reset failure: Content-Security-Policy silently blocking the browser's connection to Supabase, unrelated to the recovery link/token or prefetching

- The owner sent a genuinely fresh, unexpired, valid `type=recovery` session hash — no `error` param, real `access_token`/`refresh_token` — and the page still showed the generic "invalid or expired" fallback. Rather than accept that at face value, loaded the exact URL directly in the browser tool (observe-only, never touched or submitted anything) and read the console: `Connecting to 'https://vxvpxywszskxcugwpsch.supabase.co/auth/v1/user' violates the following Content Security Policy directive: "connect-src 'self'". The action has been blocked.` — the browser was never able to reach Supabase's own API to validate the token at all. `getSession()`/`onAuthStateChange` both fail silently under a blocked `fetch`, which the page's own 3-second-timeout fallback then correctly (from its own narrow perspective) reports as "invalid or expired" — a completely different cause producing an identical-looking symptom to every prior diagnosis in this saga.
- Root cause: `next.config.ts` calls `securityHeaders()` with no `connectSrc` at all, applied uniformly to every route. `staff/reset-password/page.tsx` and `staff/reset-password/confirm/page.tsx` (both D-059) are the first browser code in this entire app that ever calls Supabase's API directly from the client — every other Supabase Auth use (`modules/integrations/supabase-auth-client.ts`, real staff sign-in, D-050) happens server-side inside API routes, which CSP does not restrict at all. `headers.ts`'s own `connectSrc` doc comment had already named this exact gap ("populate this before... a live Supabase browser client are... unwired") but was never acted on when that client was actually wired in — a real miss, corrected here along with the code.
- Fixed in `next.config.ts`: a new `supabaseConnectSrc()` helper adds the configured Supabase project's own origin (derived from `NEXT_PUBLIC_SUPABASE_URL` via `new URL(...).origin`, never a hardcoded project ref, so this stays correct across environments) to `connect-src`, falling back to `'self'`-only (unchanged prior behavior) when Supabase isn't configured — this sandbox and CI included, so an unconfigured build still succeeds. `headers.ts`'s doc comment updated to match reality.
- This is the same structural pattern as D-059's env-var and hydration bugs before it: a real capability (a live browser-side Supabase client) got wired in without every downstream system that had assumed "no browser code calls Supabase" being updated to match — CSP here, client-bundle inlining and SSR-safety before it. All three were only found by actually exercising the real, live accept-path end to end against production, not by code review or unit tests alone.
- Evidence: `npm run typecheck`/`npm run lint` clean; full `npm run verify` passes (`REAL_EXIT_CODE:0`, confirmed directly from the background command's own captured output rather than trusting a task-notification summary alone — an earlier run in this same fix appeared to report success while actually having stopped early on a `prettier --check` formatting issue, masked by piping through `tail`, which is exactly the kind of pitfall this double-check exists to catch); production build lists both reset-password routes as correctly static; live-verified against the real deployed site after redeploy — the `Content-Security-Policy` response header's `connect-src` directive now includes the Supabase project origin alongside `'self'`, where it was `'self'` only before.

## D-058 — Fixed the notFound() 200-status bug at the proxy layer, a real currently-live defect tracked since Step 39

- Decision: `src/proxy.ts` now checks every `/(en|ur)/:path*` request against `KNOWN_LOCALE_PAGES` (`book`/`concierge`/`event`/`menu`/`privacy`/`visit`, one segment deep — the exact real directories under `src/app/[locale]/`) before any rendering starts, and self-rewrites with `{ status: 404 }` when the path doesn't match. Researched properly before implementing, not guessed: confirmed via the actual unanswered Next.js team GitHub discussion (`vercel/next.js#70170`) that there is no official fix, and the one real-world workaround pattern (a pre-render existence check at the middleware/proxy layer, since streaming has already locked in a `200` status by the time a Suspense-wrapped `notFound()` resolves deeper in the tree) is exactly what got implemented here.
- The one real risk this design intentionally takes on — `KNOWN_LOCALE_PAGES` is a second source of truth for "what page exists," independent of the actual `page.tsx` files by necessity (the check must run *before* rendering, so it can't inspect the render tree) — is closed by `tests/unit/proxy-known-pages.test.ts`, which fails CI the moment a page directory is added or removed without the list being updated to match, turning silent drift into an immediate, loud test failure instead. A second test guards the `config.matcher`'s hardcoded `(en|ur)` alternation (Next.js requires `matcher` to be statically analyzable, so it can't reference `LOCALES` directly) against drifting from the real `LOCALES` constant.
- Scope, confirmed empirically, not assumed: an *unsupported* locale (`/fr`) already 404s correctly today — `[locale]/page.tsx`'s own `isSupportedLocale` check sits outside the broken code path entirely (confirmed via the existing `tests/e2e/errors.spec.ts` test, unchanged, still passing). ## D-052 — Real bug found live in staging while verifying D-051 — **correction: the stated root cause was wrong, see D-053** — `GET /api/takeaway/cart` could be statically pre-rendered at build time, freezing its feature-flag response until a genuinely fresh rebuild — fixed with `export const dynamic = 'force-dynamic'`

- Decision: after D-051 deployed, live verification against staging found `FEATURE_BOOKING_REQUESTS`/`FEATURE_EVENT_REQUESTS` correctly reading `true` once the owner fixed a real Vercel Production-scoping gap for those two — but `FEATURE_TAKEAWAY_REQUESTS` kept returning `FEATURE_DISABLED` on `GET /api/takeaway/cart` specifically, even after the owner confirmed the same key/value/Production-checkbox/no-duplicate-row state that fixed the other two, across several redeploys. Testing other `takeaway` routes (`POST /api/takeaway/review`, `POST /api/takeaway/cart/items`) showed them correctly reading the flag as `true` — isolating the problem to one specific route, not the environment variable.
- Root cause: `GET /api/takeaway/cart` is the only `GET` route handler in this codebase whose first branch (the new feature-flag check) can return a response without ever reading a cookie/header through a `next/headers`-tracked API — every other route in the app reaches that immediately, so none had ever been exposed to this. Left implicit, Next.js can treat a `GET` route handler shaped like that as statically renderable and bake its output in at *build time* rather than executing it fresh per request — the same underlying class of bug as Step 43's `NEXT_PUBLIC_APP_URL` build-cache trap (D-047), just applied to a route handler's output instead of a client-bundle constant. - Fixed with one line: `export const dynamic = 'force-dynamic'` on that route only, the standard, documented Next.js mechanism for exactly this situation. This removes the route from any build-time caching path entirely — it now always executes fresh per request, matching every other route's existing (implicit) behavior. No other route needed this, confirmed by a source-wide check finding zero existing uses of `dynamic = 'force-dynamic'` anywhere in the project before this.
- A useful operational lesson recorded alongside D-047's: not just `NEXT_PUBLIC_*` client-bundle inlining, but *any* Next.js output computed at build time (including a naively-shaped `GET` Route Handler) can silently freeze against runtime env var changes — worth checking for on any future `GET` route whose early-return path doesn't immediately touch a dynamic API.
- Evidence: local `npm run build`'s route table (`ƒ` = dynamic) doesn't reproduce the exact staging conditions that triggered this (this sandbox has no real `FEATURE_TAKEAWAY_REQUESTS` value to build against), so this was diagnosed and fixed from live behavior and Next.js's documented static/dynamic rules, not locally reproduced — the fix itself (`force-dynamic`) is unambiguously correct regardless. 1092 unit tests unaffected; full `npm run verify` clean.

FROM anon, authenticated, service_role` (closes the gap for every *future* migration's tables, not just today's 28), then `REVOKE ALL ... FROM anon, authenticated` on every existing table/view followed by `grants.sql`'s own `GRANT` statements re-applied verbatim — restoring the exact originally-documented state rather than computing a diff. `service_role`'s correct full-access grant (it bypasses RLS by design) is untouched throughout. Verified, not assumed: `db:test:rls` and `db:test:schema` both re-run clean post-fix; `confirmation_tokens`/`idempotency_keys` direct grant inspection now genuinely shows zero `anon`/`authenticated` privileges, true for the first time since Step 10's own claim.
- The backup/restore drill mechanics themselves took five iterations to reach a clean, production-representative result — each iteration a real, kept finding, not discarded friction: (1) dump `--schema=public` only, never the whole database, since a full dump captures Supabase's own internal `auth`/`storage`/`realtime`/`vault` schemas and restoring produces dozens of harmless-but-noisy conflicts against infrastructure this application doesn't own; (2) never use `pg_dump --no-privileges` — it silently strips every `GRANT` statement, producing a *more* broken restored state (zero client access at all) than even the bug above; (3) never pre-create the target schema before restoring — `pg_dump`'s own output already includes `CREATE SCHEMA public`, so the disaster simulation must be a bare `DROP SCHEMA ... CASCADE` with nothing recreated; (4) `ALTER DEFAULT PRIVILEGES` replays with a permission error through a plain reconnection even though it applies cleanly through the Supabase CLI's own migration-apply path — a narrow, confirmed-benign local role-hierarchy quirk (affects only *future* default grants, never existing data/grants), explicitly not expected from Supabase Pro's real managed restore mechanism, documented rather than silently worked around.

## D-029 — Step 25 outbox dispatcher: one shared, atomically-claimed outbox store across all three entities; Supabase Realtime is deferred (D-017), polling the durably-dispatched result is the actual delivery guarantee for now (ADR-0007)

- Decision: `OutboxEvent` (`lib/domain/outbox.ts`) gained `id`/`version` — nothing before this step ever needed to address one specific outbox row, only append and bulk-read. `lib/domain/outbox-store.ts`'s `OutboxStore` adds `claimBatch` (one atomic conditional operation claiming due-`PENDING`-or-stale-`CLAIMED` rows, oldest first — the exact Step 21 lesson applied here: never a separate read-then-write) plus `markDelivered`/`markRetry`/`markTerminal`, each version-checked. `lib/domain/outbox-dispatcher.ts`'s `runDispatchCycle` claims a bounded batch and resolves every claim to `DELIVERED`, retried with bounded exponential backoff, or `FAILED` (terminal) once `maxAttempts` is reached — a row is never left `CLAIMED` with nothing decided, and a row with no registered handler for its `destination` fails terminal immediately rather than being retried forever for a handler that will never exist.
- One outbox, not three: `data-model-v2.md` §6 has a single `outbox_events` table, not one per entity, so `modules/{takeaway,bookings,events}/deps.ts` now all point their `outbox` field at one shared singleton (`modules/notifications/deps.ts`) instead of each building its own private `createInMemorySink()`. This lets one dispatcher drain every entity's notifications in one pass, matching the real schema, and required no type changes to `submission-service.ts`/`staff-transition.ts` (both still declare `outbox: AppendOnlySink<OutboxEvent>`; `OutboxStore` structurally satisfies that shape).
- What handles a claimed event: `modules/staff/notification-handlers.ts`'s `staff_notification` handler (the only destination in use today — ADR-0007: "the outbox schema is destination/payload-agnostic," so a future channel is an additive registry entry, not a rewrite) upserts into `modules/staff/notification-store.ts` by the outbox event's own id, which is what makes it idempotent — the dispatcher may invoke a handler twice for the same event if the process crashes between the handler succeeding and the row being marked `DELIVERED` (the same at-least-once ambiguity any such system has), and an upsert-by-id absorbs that without a duplicate.
- Realtime is explicitly deferred, not built: no live Supabase project exists (D-017), so `app/staff/dashboard.tsx` polls `GET /api/staff/notifications` instead of subscribing to a channel. This is not a lesser substitute for what the runbook step asks — ADR-0007 itself frames Realtime as "a speed-up, not the delivery guarantee," and the outbox's actual guarantee (a row reaches `DELIVERED` and becomes durably queryable) is exactly what polling already observes; Realtime would only make staff notice faster, a UX improvement to add once a live project exists, not a correctness gap today.
- The cron trigger: `app/api/cron/outbox-dispatch` (`GET`, authenticated via `Authorization: Bearer $CRON_SECRET` — `deployment-target.md` names this exact pattern for "authenticated outbox/retention jobs") runs one bounded cycle and returns redacted counts only (claimed/delivered/retried/terminal — never payloads or guest data). Added `lib/env.server.ts`'s `parseCronSecret` (returns `undefined` rather than throwing, unlike `parseSessionSecret`/`parseAppUrl` — a missing `CRON_SECRET` should mean "reject every request," not a 500) and `lib/security/cron-auth.ts`'s `verifyCronAuthHeader` (constant-time comparison, same reasoning as every other secret comparison in this codebase; `false` whenever the secret itself is unconfigured, never "accept anything"). Safe to invoke concurrently or in rapid succession — `claimBatch`'s atomicity is what makes overlapping invocations safe, not anything in the route itself. The actual Vercel Cron schedule is a deployment-step concern (Step 46), not built here.
- Evidence: 34 new focused tests covering exactly the runbook's own evidence bullet — worker overlap (two genuinely concurrent `claimBatch`/`runDispatchCycle` calls never both claim or invoke a handler for the same row), crash/retry (a stale, unresolved claim is reclaimed after `staleClaimMs`; a transient failure retries with a growing backoff and succeeds once due), poison message (a handler that always throws is marked terminal at exactly `maxAttempts` and never claimed or invoked again after that), and terminal-failure visibility (`lastError`/`failedAt` recorded and queryable via `list()`) — plus the notification handler's idempotent upsert and the cron auth header's fail-closed matrix. 684 tests total; full `npm run verify` passes, including a production build listing `/api/cron/outbox-dispatch` and `/api/staff/notifications`. ## D-025 — Fixed a real concurrency race in Step 19's idempotency/confirmation-token stores; atomicity/rollback beyond that is deferred to a real DB

- Decision: `lib/domain/idempotency.ts`'s `IdempotencyStore` and `lib/domain/confirmation-token.ts`'s `ConfirmationTokenStore` each replaced a two-step "read, decide, write" (`find`+`begin`, `find`+`markUsed`) with one atomic store operation (`findOrBegin`, `claimIfUnused`) that a real adapter must implement as a single conditional write (e.g. `UPDATE ... WHERE used_at IS NULL RETURNING *`), not a separate read-then-write.
- Why: Runbook Step 21's evidence bullet ("concurrency, double-click, retry, rollback, and atomicity integration tests") is explicitly *not* satisfied by Step 19's sequential tests — checking directly, an explicit `Promise.all` (two calls fired together, not one awaited after the other) proved both the idempotency store and the confirmation-token store let two truly concurrent callers both pass the "not yet started"/"not yet used" check before either wrote back, because `await`ing an async store call always yields to the microtask queue even when the call's own body is synchronous. Sequential tests never exercise this: each call fully completes (including its writes) before the next one starts, so the interleaving the fix targets never happens. `versioned-store.ts`'s `updateIfVersionMatches` was already correct by the same reasoning in reverse — its whole body has no internal `await`, so two calls can never interleave even when invoked concurrently.
- What "atomicity/rollback" still means here: for the in-memory stores, a genuine multi-step failure part-way through (e.g. the second of several snapshot-line writes throwing) has no real rollback, because in-memory `Map`/array writes cannot fail and there is no live database transaction (D-023/D-017) to roll back. `submission-service.ts` already does all validation and computation before any write, so no write happens for a request that was going to fail anyway — that is the property provable now; true multi-write atomicity is a property the real Postgres adapter's transaction must provide later, not something achievable in-memory.
- Evidence: 5 new focused tests using `Promise.all` (not sequential awaits) — a genuine double-click on the same idempotency key/confirmation token resolves to exactly one success and one `IDEMPOTENCY_CONFLICT`/`NOT_FOUND`, never two successes and never zero; a `FAILED` record with a *different* fingerprint still blocks as a mismatch rather than being silently retried. 563 tests total; full `npm run verify` passes.

- Evidence: manual browser check of `/en/nonexistent` (now correctly `lang="en" dir="ltr"`, full header/footer, inside `[locale]/not-found.tsx`) versus `/xyz` (still correctly the bare root fallback, since the locale segment itself is invalid).

## D-019 — Theme preference is a separate, unsigned, isomorphic cookie; `/[locale]` is now dynamic

- Decision: the Day/Night preference (`lib/theme/`) is its own cookie (`cladium_theme`), deliberately unsigned and readable/writable by client JS — unlike the locale preference cookie (`lib/i18n/preference-cookie.ts`), which is signed and `HttpOnly`. `app/[locale]/layout.tsx` now calls `cookies()` to render the correct `data-theme` on first paint, which makes `/en` and `/ur` dynamically rendered (`ƒ`) instead of statically prerendered (`●`).
- Why: theme-mode.md states the theme is "separate from language" with no security/routing consequence, unlike locale (open-redirect risk). Signing would buy nothing and would block the instant, no-reload client-side toggle the spec requires (an `HttpOnly` cookie can't be read/written from `document.cookie`). Reading the cookie server-side for a flash-free initial render is unavoidably a per-request operation, so static prerendering of the locale routes is no longer possible — an accepted, necessary trade-off, not a regression to fix later.
- Evidence: `tests/unit/theme.test.ts`, `tests/unit/theme-preference-cookie.test.ts`, `tests/unit/theme-tokens.test.ts`; live browser check of `/en` and `/ur` in both themes, including instant client-side switching (verified with the CSS transition temporarily disabled, since the test harness's hidden preview pane doesn't produce compositor frames to drive a live transition — a tooling artifact, confirmed not to affect a normally-visible browser).

## D-018 — Route group per root layout, not a shared one above `[locale]`

- Decision: the un-localized `/` fallback (`app/(root-fallback)/{layout,page}.tsx`) lives in its own route group with its own `<html>`/`<body>`, instead of a single `app/layout.tsx` shared with `app/[locale]/layout.tsx`.
- Why: Next.js only merges a nested duplicate `<html>` tag's *missing* attributes onto the outer one — it never overwrites an attribute the outer tag already set. The prior shared `app/layout.tsx` set `<html lang="en">` unconditionally and sat above `app/[locale]/layout.tsx` in the tree, so every `/ur` route rendered `lang="en" dir="rtl"` in the browser: `dir` (unset outer) merged through, `lang` (set outer) silently won. Found by loading `/ur` in a real browser and reading `document.documentElement`, not by the unit/build gates, which don't render a DOM.
- Evidence: `npm run verify` passes with the route group in place; manual browser check of `/en` and `/ur` shows correct `lang`/`dir` on both.
