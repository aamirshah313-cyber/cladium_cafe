## D-033 — Step 29 agent evaluation harness: `requiresLiveModel` splits deterministic orchestrator/policy guarantees (run and CI-gated now) from genuine model-judgment cases (fully specified, versioned, visibly skipped)

- Decision: `modules/evals/` — `types.ts` (`EvalCase`/`EvalTranscript`/`EvalCaseResult`/`EvalReport`), `assertions.ts` (pure `EvalAssertion` factories — `replyContains`/`replyNeverContains`/`escalates`/`toolWasCalled`/`toolWasNeverCalled`/`systemPromptNeverChanged`/`systemPromptContains`/`pendingConfirmationHasKind`/`noPendingConfirmation`/`reviewNeverQuotesAPrice`), and `runner.ts` (`runEvalCase`/`runEvalSuite`) run every case through the *real* `orchestrateTurn` (Step 27) against a scripted fake `ChatClient` — never a reimplementation of the orchestrator's own logic, the same fake-client pattern `tests/unit/concierge-orchestrator.test.ts` already established.
- Every `EvalCase` declares `requiresLiveModel: boolean`. `false` cases are scored deterministically right now: real tool dispatch (including the real Step 19 submission service via `prepareBookingRequest`/`prepareEventRequest`), so their assertions check genuine orchestrator/policy output, not text the case itself supplies — e.g. `reviewNeverQuotesAPrice()` inspects the actual `EventReview` object a real `prepareEventRequest` call produced (structurally has no price field at all — `modules/events/submission-service.ts`), and `systemPromptContains(...)` inspects the actual `CONCIERGE_SYSTEM_POLICY` string the orchestrator sent, not this suite's own prose. `true` cases (bilingual comprehension, tool selection from ambiguity, live injection resistance) cannot run without a live `ANTHROPIC_API_KEY` (D-031) — `runEvalCase` returns them `skipped: true` with an explicit reason, never faked, never silently dropped from the suite's totals.
- `src/modules/evals/cases/` covers all 11 runbook-named categories (English, Urdu script, Roman Urdu, ambiguity, injection, prices, policies, availability, confirmation, handoff, tool selection) with a mix of both kinds — 27 cases total. Every `requiresLiveModel: false` case is `critical: true`, because each encodes a structural `CLAUDE.md` guarantee (never invent a price, never confirm availability, no submit tool reachable by the model, system prompt immune to injection, the tool-call budget really terminates the loop). Every `requiresLiveModel: true` case is `critical: false` in the current suite, since a skipped case can neither pass nor fail — marking one critical would make the CI gate meaningless.
- `tests/unit/evals.test.ts` is the CI gate: fails the build on any critical, *runnable* (non-skipped) failure, plus data-integrity checks (unique ids, all 11 categories present, every runnable case has scripted turns). `cladium-research/agent/eval-policy.md` documents the non-critical threshold ("zero tolerance for a runnable critical failure, no gate at all on a case that cannot run here") and the review process for later, once a live key exists — ties back to `release-gates-v2.md` Gate 5's "critical policy evals pass 100% in English, Urdu script, and Roman Urdu," which still needs the `requiresLiveModel: true` cases actually run before launch (tracked in TASKS.md).
- Evidence: 6 new tests in `tests/unit/evals.test.ts` plus the 27-case suite itself (12 of 27 cases skipped as `requiresLiveModel: true`, 15 run and pass, zero critical failures). 810 tests total (66 test files); full `npm run verify` passes. No new route; nothing to live-verify in the browser this step (same as Step 26).

## D-031 — Step 27 server-side chat orchestration: a real, typechecked Anthropic adapter behind a provider-neutral interface; bounded tool/token/time loop with a safe fallback, never live-called (no API key in this sandbox)

- Decision: installed `@anthropic-ai/sdk`. `modules/integrations/anthropic-client.ts`'s `ChatClient` is the provider-neutral interface (`sendMessage`) `modules/concierge/orchestrator.ts` depends on — never the SDK's own types directly (ADR-0005's reversibility goal: "reimplementing the orchestration adapter only"). `createAnthropicChatClient()` never throws at construction; `ANTHROPIC_API_KEY` (`parseAnthropicApiKey`, new) is only read inside `sendMessage`, so importing the module — which `modules/concierge/deps.ts` does at process start — can never crash an unrelated route. The three translation functions (`to`/`fromAnthropicContent`, `fromAnthropicStopReason`) are exported and directly unit-tested, since the real API call itself cannot be exercised without a live key here.
- `modules/concierge/orchestrator.ts`'s `orchestrateTurn` is one bounded guest turn: rate-limit (reusing Step 12's `createInMemoryRateLimiter` unchanged) → load server-held history (`conversation-store.ts`, never browser-supplied — "browser history is untrusted and cannot authorize actions") → a tool-call loop bounded by `MAX_TOOL_CALLS_PER_TURN` (5), cumulative `MAX_TOTAL_TOKENS_PER_TURN` (8000), and `TURN_TIMEOUT_MS` (20s, checked via injectable `now()` so tests never wait in real time) → persist only the turn's final user/assistant text, never the intermediate tool-call scaffolding. Every failure mode — a poison tool-use loop, a budget/deadline breach, a thrown exception from the chat client — resolves to the same shape: a plain-language reply plus `escalate: true`, pointing at the official WhatsApp number, never a thrown exception or leaked internal error detail.
- `system` is always exactly `CONCIERGE_SYSTEM_POLICY`, never built from `input.userMessage` or history, and every tool result only ever enters the message array as a `tool_result` block — structurally, nothing a guest types (including an explicit "ignore previous instructions" attempt) can ever be elevated to instruction-level trust. Verified directly: a test asserts the `system` field passed to the (fake) chat client is byte-identical across calls regardless of adversarial `userMessage` content.
- `modules/concierge/tool-registry.ts` pairs each Step 26 tool with a hand-written JSON schema (`additionalProperties: false`, never auto-derived from zod, so the "reject unknown properties" guarantee can never silently regress) and the same zod schema that already enforced it. `dispatchToolCall` is the one place a model-supplied tool name/input ever reaches a real function call: an unknown name is an orchestrator-level `NOT_FOUND`; a schema-invalid input for a *known* tool instead resolves as a self-correctable `{error}` tool_result the model can retry from — a deliberate choice, since crashing the whole turn over one malformed tool call would be worse than letting the model see the validation error and try again.
- Logging never carries raw chat content: `errorType` (a constructor name only) replaces the exception's own `.message` in the one place an exception is caught, and turn-completion telemetry logs only `correlationId`/`toolCalls`/`escalate` counts — verified by asserting the raw `userMessage`/`reply` text (including embedded phone-number-shaped and secret-shaped strings) never appears anywhere in a fake logger's captured calls.
- No UI built this step, deliberately: Step 27's own title is "server-side chat orchestration," and CLAUDE.md's "Ask Cladium Concierge" CTA is more naturally Step 28's job ("concierge draft actions and confirmation") once the concierge can also propose requests, not only answer questions — the same "build the deterministic layer now, the UI once there's something it actually needs to do" pattern already used for D-024 (takeaway UI deferred to menu publication) and D-030 (Step 26 shipped no UI either). The route itself (`POST /api/concierge/chat`) is real and live-verified for its fail-closed path only, same standing `SESSION_SECRET`-unconfigured limitation as every guest-mutating route since Step 20.
- Evidence: 4 new test files covering the runbook's own evidence bullet — cross-session isolation, prompt-injection structural guarantees, loop exhaustion, timeout, PII-safe telemetry, and cost-limit tests all pass against a fake `ChatClient`/`Logger`, plus the Anthropic content-translation round-trip and tool-registry validation matrix. 779 tests total; full `npm run verify` passes, including a production build listing `/api/concierge/chat` and a client-bundle scan confirming no Anthropic SDK/key material reaches the browser. Live check (after a dev-server restart worked around a one-time Turbopack new-directory route-discovery delay, not a code issue — the route was already correctly listed in the production build beforehand) confirmed the endpoint fails closed with a safe generic 500 and no stack trace, `SESSION_SECRET` unconfigured in this sandbox.

## D-029 — Step 25 outbox dispatcher: one shared, atomically-claimed outbox store across all three entities; Supabase Realtime is deferred (D-017), polling the durably-dispatched result is the actual delivery guarantee for now (ADR-0007)

- Decision: `OutboxEvent` (`lib/domain/outbox.ts`) gained `id`/`version` — nothing before this step ever needed to address one specific outbox row, only append and bulk-read. `lib/domain/outbox-store.ts`'s `OutboxStore` adds `claimBatch` (one atomic conditional operation claiming due-`PENDING`-or-stale-`CLAIMED` rows, oldest first — the exact Step 21 lesson applied here: never a separate read-then-write) plus `markDelivered`/`markRetry`/`markTerminal`, each version-checked. `lib/domain/outbox-dispatcher.ts`'s `runDispatchCycle` claims a bounded batch and resolves every claim to `DELIVERED`, retried with bounded exponential backoff, or `FAILED` (terminal) once `maxAttempts` is reached — a row is never left `CLAIMED` with nothing decided, and a row with no registered handler for its `destination` fails terminal immediately rather than being retried forever for a handler that will never exist.
- One outbox, not three: `data-model-v2.md` §6 has a single `outbox_events` table, not one per entity, so `modules/{takeaway,bookings,events}/deps.ts` now all point their `outbox` field at one shared singleton (`modules/notifications/deps.ts`) instead of each building its own private `createInMemorySink()`. This lets one dispatcher drain every entity's notifications in one pass, matching the real schema, and required no type changes to `submission-service.ts`/`staff-transition.ts` (both still declare `outbox: AppendOnlySink<OutboxEvent>`; `OutboxStore` structurally satisfies that shape).
- What handles a claimed event: `modules/staff/notification-handlers.ts`'s `staff_notification` handler (the only destination in use today — ADR-0007: "the outbox schema is destination/payload-agnostic," so a future channel is an additive registry entry, not a rewrite) upserts into `modules/staff/notification-store.ts` by the outbox event's own id, which is what makes it idempotent — the dispatcher may invoke a handler twice for the same event if the process crashes between the handler succeeding and the row being marked `DELIVERED` (the same at-least-once ambiguity any such system has), and an upsert-by-id absorbs that without a duplicate.
- Realtime is explicitly deferred, not built: no live Supabase project exists (D-017), so `app/staff/dashboard.tsx` polls `GET /api/staff/notifications` instead of subscribing to a channel. This is not a lesser substitute for what the runbook step asks — ADR-0007 itself frames Realtime as "a speed-up, not the delivery guarantee," and the outbox's actual guarantee (a row reaches `DELIVERED` and becomes durably queryable) is exactly what polling already observes; Realtime would only make staff notice faster, a UX improvement to add once a live project exists, not a correctness gap today.
- The cron trigger: `app/api/cron/outbox-dispatch` (`GET`, authenticated via `Authorization: Bearer $CRON_SECRET` — `deployment-target.md` names this exact pattern for "authenticated outbox/retention jobs") runs one bounded cycle and returns redacted counts only (claimed/delivered/retried/terminal — never payloads or guest data). Added `lib/env.server.ts`'s `parseCronSecret` (returns `undefined` rather than throwing, unlike `parseSessionSecret`/`parseAppUrl` — a missing `CRON_SECRET` should mean "reject every request," not a 500) and `lib/security/cron-auth.ts`'s `verifyCronAuthHeader` (constant-time comparison, same reasoning as every other secret comparison in this codebase; `false` whenever the secret itself is unconfigured, never "accept anything"). Safe to invoke concurrently or in rapid succession — `claimBatch`'s atomicity is what makes overlapping invocations safe, not anything in the route itself. The actual Vercel Cron schedule is a deployment-step concern (Step 46), not built here.
- Evidence: 34 new focused tests covering exactly the runbook's own evidence bullet — worker overlap (two genuinely concurrent `claimBatch`/`runDispatchCycle` calls never both claim or invoke a handler for the same row), crash/retry (a stale, unresolved claim is reclaimed after `staleClaimMs`; a transient failure retries with a growing backoff and succeeds once due), poison message (a handler that always throws is marked terminal at exactly `maxAttempts` and never claimed or invoked again after that), and terminal-failure visibility (`lastError`/`failedAt` recorded and queryable via `list()`) — plus the notification handler's idempotent upsert and the cron auth header's fail-closed matrix. 684 tests total; full `npm run verify` passes, including a production build listing `/api/cron/outbox-dispatch` and `/api/staff/notifications`. Live check confirmed the cron endpoint fails closed (401, safe generic message) with no `Authorization` header/`CRON_SECRET` configured, and `/staff`'s sign-in page still renders correctly with no regression.

Server Actions were considered and rejected in favor of the already-proven client-fetch + JSON API pattern from Step 20 — introducing a new, untested request-handling pattern in the same step as new business logic would have mixed two kinds of risk with no offsetting benefit.
- Booking-specific details: `requestedDate`/`requestedTime` use dedicated regex schemas (`lib/schemas/common.ts`); "today or later" is checked via `modules/bookings/request-window.ts`'s `isTodayOrFutureDate` (an injectable-`now` pure function, unit-tested directly) rather than only inline in the zod `.refine()`, so the business rule stays independently testable from the boundary-parsing wiring. The `/book?seating=treehouse` query param only pre-selects the form's seating radio (Home page's "Request Treehouse Seating" CTA) — treehouse capacity remains staff-confirmed regardless, per `SEATING_POLICY_TEXT`. The confirmed-stage copy explicitly says "not yet a confirmed reservation," matching `data-model-v2.md` §5 ("a requested time is not availability").
- Reused without re-testing at this layer: `runIdempotent`/`findOrBegin` and `claimIfUnused`'s atomic concurrency fix (D-025) — booking's own concurrency tests (mirroring takeaway's `Promise.all` double-click tests) confirm the generic mechanism holds for a second entity, not that the mechanism itself needed re-deriving.
- Evidence: 573 tests total (10 new: `request-window` date-boundary tests plus `booking-submission-service` happy-path/idempotent-replay/concurrency/bad-token tests, mirroring takeaway's Step 21 shape); full `npm run verify` passes, including production build listing `/[locale]/book`, `/api/bookings/review`, `/api/bookings/submit`, and `/api/session/csrf`. Live end-to-end happy-path verification remains blocked by the same standing limitation as Steps 20–21 (`.env.local`/`SESSION_SECRET` cannot be set in this sandbox); structural/build verification and unit tests are the evidence for this step.

## D-025 — Fixed a real concurrency race in Step 19's idempotency/confirmation-token stores; atomicity/rollback beyond that is deferred to a real DB

- Decision: `lib/domain/idempotency.ts`'s `IdempotencyStore` and `lib/domain/confirmation-token.ts`'s `ConfirmationTokenStore` each replaced a two-step "read, decide, write" (`find`+`begin`, `find`+`markUsed`) with one atomic store operation (`findOrBegin`, `claimIfUnused`) that a real adapter must implement as a single conditional write (e.g. `UPDATE ... WHERE used_at IS NULL RETURNING *`), not a separate read-then-write.
- Why: Runbook Step 21's evidence bullet ("concurrency, double-click, retry, rollback, and atomicity integration tests") is explicitly *not* satisfied by Step 19's sequential tests — checking directly, an explicit `Promise.all` (two calls fired together, not one awaited after the other) proved both the idempotency store and the confirmation-token store let two truly concurrent callers both pass the "not yet started"/"not yet used" check before either wrote back, because `await`ing an async store call always yields to the microtask queue even when the call's own body is synchronous. Sequential tests never exercise this: each call fully completes (including its writes) before the next one starts, so the interleaving the fix targets never happens. `versioned-store.ts`'s `updateIfVersionMatches` was already correct by the same reasoning in reverse — its whole body has no internal `await`, so two calls can never interleave even when invoked concurrently.
- What "atomicity/rollback" still means here: for the in-memory stores, a genuine multi-step failure part-way through (e.g. the second of several snapshot-line writes throwing) has no real rollback, because in-memory `Map`/array writes cannot fail and there is no live database transaction (D-023/D-017) to roll back. `submission-service.ts` already does all validation and computation before any write, so no write happens for a request that was going to fail anyway — that is the property provable now; true multi-write atomicity is a property the real Postgres adapter's transaction must provide later, not something achievable in-memory.
- Evidence: 5 new focused tests using `Promise.all` (not sequential awaits) — a genuine double-click on the same idempotency key/confirmation token resolves to exactly one success and one `IDEMPOTENCY_CONFLICT`/`NOT_FOUND`, never two successes and never zero; a `FAILED` record with a *different* fingerprint still blocks as a mismatch rather than being silently retried. 563 tests total; full `npm run verify` passes.

## D-020 — A catch-all route, not just `not-found.tsx`, is required for locale-correct 404s

- Decision: `app/[locale]/[...rest]/page.tsx` calls `notFound()` unconditionally for any path under a valid locale that doesn't match a real route.
- Why: `app/[locale]/not-found.tsx` alone only fires when a component *inside* an already-matched route explicitly calls `notFound()`. A request to a path with no matching route at all (e.g. `/en/nonexistent`, before any deeper pages exist) is never routed into `[locale]/layout.tsx` in the first place, so Next.js falls straight through to the self-sufficient root `app/not-found.tsx` — losing correct `lang`/`dir`/`data-theme` and the site header/footer. Found via a live browser check (`document.documentElement`'s `dir` attribute was silently missing), not by the build or any automated test — same category of bug as D-018.
- Evidence: manual browser check of `/en/nonexistent` (now correctly `lang="en" dir="ltr"`, full header/footer, inside `[locale]/not-found.tsx`) versus `/xyz` (still correctly the bare root fallback, since the locale segment itself is invalid).

## D-019 — Theme preference is a separate, unsigned, isomorphic cookie; `/[locale]` is now dynamic

- Decision: the Day/Night preference (`lib/theme/`) is its own cookie (`cladium_theme`), deliberately unsigned and readable/writable by client JS — unlike the locale preference cookie (`lib/i18n/preference-cookie.ts`), which is signed and `HttpOnly`. `app/[locale]/layout.tsx` now calls `cookies()` to render the correct `data-theme` on first paint, which makes `/en` and `/ur` dynamically rendered (`ƒ`) instead of statically prerendered (`●`).
- Why: theme-mode.md states the theme is "separate from language" with no security/routing consequence, unlike locale (open-redirect risk). Signing would buy nothing and would block the instant, no-reload client-side toggle the spec requires (an `HttpOnly` cookie can't be read/written from `document.cookie`). Reading the cookie server-side for a flash-free initial render is unavoidably a per-request operation, so static prerendering of the locale routes is no longer possible — an accepted, necessary trade-off, not a regression to fix later.
- Evidence: `tests/unit/theme.test.ts`, `tests/unit/theme-preference-cookie.test.ts`, `tests/unit/theme-tokens.test.ts`; live browser check of `/en` and `/ur` in both themes, including instant client-side switching (verified with the CSS transition temporarily disabled, since the test harness's hidden preview pane doesn't produce compositor frames to drive a live transition — a tooling artifact, confirmed not to affect a normally-visible browser).

## D-018 — Route group per root layout, not a shared one above `[locale]`

- Decision: the un-localized `/` fallback (`app/(root-fallback)/{layout,page}.tsx`) lives in its own route group with its own `<html>`/`<body>`, instead of a single `app/layout.tsx` shared with `app/[locale]/layout.tsx`.
- Why: Next.js only merges a nested duplicate `<html>` tag's *missing* attributes onto the outer one — it never overwrites an attribute the outer tag already set. The prior shared `app/layout.tsx` set `<html lang="en">` unconditionally and sat above `app/[locale]/layout.tsx` in the tree, so every `/ur` route rendered `lang="en" dir="rtl"` in the browser: `dir` (unset outer) merged through, `lang` (set outer) silently won. Found by loading `/ur` in a real browser and reading `document.documentElement`, not by the unit/build gates, which don't render a DOM.
- Evidence: `npm run verify` passes with the route group in place; manual browser check of `/en` and `/ur` shows correct `lang`/`dir` on both.
